# PRD — Visit Busan (부산 눈치게임)

## 1. 개요
부산 지역별 혼잡도를 시각화하고, 혼잡도 기반 핫플레이스/숨은명소를 추천하며, 스팟별 혼잡도 예보와 축제 정보를 제공하는 관광 웹앱.

- **현재 상태**: 메인·목록·상세 전 페이지가 실 백엔드(`https://busan-timing-backend.onrender.com`, Spring, `/v3/api-docs`로 스펙 제공)로 전환 완료. 목업 `api/forecast.ts`는 삭제됨. 대체 스팟 추천(`/suggestions`)·함께 가기 좋아요(`/companions`) 연동 완료. UI 폴리싱 진행 중(목록 카드 개편, 혼잡 배너 컴포넌트화, 페이지네이션 UX 개선 완료). 남은 미착수: 애널리틱스 연동, API 장애 폴백 UI, Header 라벨 정책 결정
- **타깃**: 부산 방문/거주자 중 혼잡을 피해 여행 동선을 짜려는 사용자

## 2. 문제 정의
- 인기 관광지는 시간대/요일에 따라 혼잡도 편차가 커서, 사전 정보 없이 방문하면 대기·인파에 시간을 낭비함
- 기존 지도 서비스는 실시간 위치 정보는 주지만 "이 구가 지금 얼마나 붐비는지"를 한눈에 보여주지 않음
- 사용자는 붐비지 않는 대안(숨은명소)을 찾기 어려움

## 3. 목표 (Goals)
1. 부산 구별 혼잡도를 지도 위에서 즉시 파악
2. 혼잡도 낮은 "숨은명소"와 인기 "핫플레이스"를 구분해 추천
3. 스팟 상세에서 요일/기간별 혼잡도 예보로 방문 시점 계획 지원
4. 검색·구 필터로 원하는 스팟을 빠르게 탐색

### Non-goals
- 실시간 인파 데이터 수집(현재도 예측치 기반 — 실시간 센서/유동인구 데이터 아님)
- 예약, 티켓팅, 길찾기 등 트랜잭션 기능
- 회원가입/로그인, 개인화 추천

## 4. 핵심 기능 (Features)

### 4.1 메인 (`/`) — 완료
- `GET /api/main`으로 구별 혼잡도·주간/월간 눈치게임 접전지·이 달의 히든 플레이스 조회 (`react-query`)
- 카카오맵에 부산 구별 폴리곤을 혼잡도 레벨(1~5) 색상으로 표시 (`KakaoMap.tsx`)
- 구 클릭 시 `/list?district={code}`로 이동
- 핫플레이스 카드(`HotPlaceCard`) / 숨은명소 카드(`HiddenPlaceCard`) 노출

### 4.2 목록 (`/list`) — 완료
- `GET /api/places`로 검색·구 필터·정렬·페이지네이션 조회 (`react-query`)
- 스팟 검색(`SearchBar`) — `?q=` 쿼리 파라미터
- 구 필터 — `?district=` 쿼리 파라미터
- 혼잡 구 선택 시 여유 구 TOP3 배너 (`CongestionBanner.tsx`) — `districtSuggestion.visible` API값으로 노출 제어, PC(스트립 버튼+팝업)·모바일(칩 배너) 분리 렌더링
- 스팟 카드 그리드 (`SpotCard.tsx`) — 이미지 하단 그라데이션 스크림 + 혼잡도 레벨 라벨(좌하단), hover 시 혼잡도 색상 border + CSS-only 화살표 애니메이션, `last7DaysAverageCongestion` 기반 bar/퍼센트 표시 ("지난 7일 평균" 명시)
- 페이지네이션 — 5페이지 고정 그룹 창(`Math.floor(page/5)*5`), 이전/다음은 그룹 단위 점프, `isFetching` 동안 grid opacity 전환

### 4.3 상세 (`/detail/:spotId`)
- **완료** — 스팟 기본정보(`GET /api/places/{id}`): 이름·주소·설명·이미지·오늘 혼잡도·주차장 검색 링크(`parkingSearchUrl`)
- **완료** — 기간별 혼잡도 예보 캘린더(`DateRangePicker` + `GET /api/places/{id}/forecast`): 달력에서 고른 구간(최대 7일)과 그 다음 7일을 함께 표시
- **완료** — 요일별 혼잡 패턴(`GET /api/places/{id}/congestion-pattern`): 요일별 평균 혼잡도, 혼잡/여유 요일 중 더 적은(눈에 띄는) 쪽을 시각적으로 강조. 백엔드가 `summary.crowdedDays`/`relaxedDays`를 내려주지만 프론트에서 레벨 기준(≥4 혼잡, ≤2 여유)으로 재계산해 덮어씀(`computeSummary`)
- **완료** — 축제(`GET /api/places/{id}/festivals`): 향후 30일과 겹치는 축제를 목록으로 노출(클릭 시 축제명 검색), 예보 캘린더에는 해당 날짜에만 도트로 표시
- **완료** — 대체 스팟 추천(`GET /api/places/{id}/suggestions`): 오늘 혼잡도 레벨 4 이상일 때만 호출/노출, "내 주변"(`nearby`, 거리 km 표시)·"취향저격"(`similar`, 카테고리 표시) 두 탭으로 구성, 각 최대 4개 카드
- **완료** — 함께 가기 좋아요(연관 관광지) (`GET /api/places/{id}/companions`): 상시 노출, 결과 4개일 때 새로고침 버튼 제공

### 4.4 혼잡도 시스템
- 혼잡도(0~100) → 레벨(1~5) → 색상/이미지/라벨 변환은 `src/utils/congestion.ts`로 통일 (신규 컴포넌트도 이 유틸 재사용, 임계값 재구현 금지)

## 5. 데이터 요구사항 (백엔드 연동 현황)
**아키텍처 정정 (2026-07-26)**: 당초 프론트가 한국관광공사/부산시 공공 OpenAPI를 직접 호출할 것으로 가정했으나, 실제로는 별도로 배포된 커스텀 백엔드(`https://busan-timing-backend.onrender.com`, Spring, `/v3/api-docs`에서 스펙 확인 가능)를 통해서만 데이터를 받는다. 이 백엔드가 내부적으로 §6의 공공 OpenAPI를 활용하는지는 확인되지 않음 — 이 저장소는 프론트엔드 전용이라 백엔드 내부 구현은 범위 밖. `mockData.ts`/`api/forecast.ts`는 활성 페이지(메인/목록/상세)에서 더 이상 참조되지 않으며, `api/forecast.ts`는 삭제됨.

| 항목 | 백엔드 엔드포인트 | 상태 | 비고 |
|---|---|---|---|
| 메인 화면 데이터 | `GET /api/main` | ✅ 완료 | 구별 혼잡도, 주간/월간 접전지, 히든 플레이스 |
| 스팟 목록/검색 | `GET /api/places` | ✅ 완료 | 키워드·구 필터·정렬·페이지네이션 |
| 스팟 기본정보 | `GET /api/places/{id}` | ✅ 완료 | 이름·주소·설명·이미지·오늘 혼잡도·`parkingSearchUrl` |
| 혼잡도 예보 | `GET /api/places/{id}/forecast?start&days` | ✅ 완료 | `selectedPeriod`(달력 선택 구간)+`followingPeriod`(다음 7일) 구조, 날짜별 `festivalIds` 포함 |
| 요일별 혼잡 패턴 | `GET /api/places/{id}/congestion-pattern` | ✅ 완료 | 요일 평균 혼잡도 + `summary.crowdedDays`/`relaxedDays`(백엔드가 유의미한 날만 선별) |
| 축제 | `GET /api/places/{id}/festivals` | ✅ 완료 | 스팟별 전체 축제 목록(날짜 필터 없음) — 프론트에서 "향후 30일 겹침"으로 목록 필터링, 예보의 `festivalIds`로 캘린더 날짜 매칭 |
| 대체 스팟 추천 (혼잡 시) | `GET /api/places/{id}/suggestions` | ✅ 완료 | `nearby`(거리 순) + `similar`(카테고리 유사) 두 배열, 레벨 4 이상일 때만 호출/노출 |
| 함께 가기 좋아요 (연관 관광지) | `GET /api/places/{id}/companions` | ✅ 완료 | 상시 조회·노출, 4개 결과 시 새로고침 버튼으로 랜덤 재조회 |
| 구 식별자 | GeoJSON `properties.code` ↔ 백엔드 `districtCode` | ✅ 완료 | 5자리 행정코드로 통일 (`26350` = 해운대구 등) |

- 지도 폴리곤: `public/busan_districts.geojson`
- 혼잡도 레벨(1~5) 산정은 백엔드가 주는 `score`(0~100)를 `src/utils/congestion.ts: getCongestionLevel`로 프론트에서 재매핑 — 백엔드 자체 `levelCode`/`label` 필드는 참고용으로만 두고 사용 안 함(레벨 산정 기준을 프론트 한 곳으로 유지)
- 5단계 혼잡도 등급(한가·여유·보통·조금 혼잡·매우 혼잡) 산정 기준은 API가 제공하지 않으므로 `src/utils/congestion.ts`의 임계값 로직을 자체 정의 — 목업 때 쓰던 임계값(40/55/70/84)을 그대로 실 데이터에도 쓰고 있음, 실측 분포로 재보정할지는 아직 논의 안 됨

## 7. 성공 지표 (KPI)

| 지표 | 정의 | 목표 | 측정 시점 |
|---|---|---|---|
| 지도→목록 전환율 | 메인 구 클릭 후 `/list` 진입 세션 비율 | ≥ 40% | M1 출시 후 |
| 검색→상세 전환율 | `/list`에서 검색/필터 사용 후 `/detail`로 이동한 비율 | ≥ 30% | M1 출시 후 |
| 숨은명소 클릭 점유율 | 숨은명소 카드 클릭 수 / (숨은명소+핫플레이스 클릭 수) | ≥ 25% | M1 출시 후 (핵심 차별 기능 검증) |
| 예보 캘린더 상호작용률 | 상세 페이지 방문 중 날짜 재선택이 1회 이상 발생한 비율 | ≥ 20% | M2 출시 후 (실 데이터 반영 후에만 의미 있음) |

- 측정 도구 미정 — GA4/Amplitude 등 애널리틱스 연동 자체가 아직 미착수(§9 M1)
- 데이터 레이어는 실 API로 전환됐지만 애널리틱스가 없어 위 지표는 여전히 정의만 된 상태 — 실측은 애널리틱스 연동 이후부터 시작

## 8. 리스크 / 미해결 이슈

### 데이터 소스 (공공 OpenAPI) 관련
> §5에서 정정했듯 아래는 원래 프론트가 직접 호출할 것으로 가정하고 쓴 리스크. 실제로는 커스텀 백엔드가 중간에 있어 아래 항목 상당수는 **백엔드 저장소의 문제**로 넘어갔다 — 이 저장소(프론트)에서 직접 검증·해결할 수 없고, 백엔드 쪽에서 확인이 필요한 항목이라는 점만 표시해둔다.

- **예측 정확도 미검증**: 한국관광공사 집중률 예측 API(또는 백엔드가 실제 쓰는 원천이 무엇이든)가 실제 부산 관광지 방문 패턴과 얼마나 맞는지 검증 안 됨 — 값이 부정확하면 "혼잡 예보" 자체의 신뢰성 문제로 직결
- **5단계 등급 산정 기준**: 백엔드가 `score`(0~100)만 내려주고, 5단계 컷오프는 프론트 `utils/congestion.ts`에서 독자적으로 정의(§5) — 백엔드 자체 `levelCode`와 프론트 등급이 100% 일치하는지 미검증
- **커버리지 공백**: 백엔드에 등록되지 않은 스팟은 혼잡도 예보 불가(예: place 90/250처럼 `congestion-pattern`이 빈 배열로 오는 케이스 확인됨), 축제도 스팟마다 유무 편차 큼
- **백엔드 안정성 (백엔드 저장소 확인 필요)**: Render 무료 티어로 배포돼 있어(`busan-timing-backend.onrender.com`) 콜드 스타트/트래픽 급증 시 응답 지연 가능성 — 프론트 쪽 캐싱·재시도·장애 폴백 UI는 아직 미구현
- **API 키/원천 데이터 관리 (백엔드 저장소 문제)**: 공공 API 키 발급·갱신 주기·이용 약관 문제는 이제 프론트가 아니라 백엔드가 직접 다룸 — 이 저장소에서는 더 이상 추적 불필요
- **상용화 조건 미확인**: 백엔드가 공모전 제출용 임시 배포인지, 실제 트래픽을 감당할 수 있는 구성인지 미확인

### 실 배포 백엔드 확인 필요 (2026-07-26 발견)
- [ ] **혼잡도 예보 가용 기간 단축 (OpenAPI 미제공 — 담당자 문의 중)**: 설계 의도는 향후 30일이나, 현재 공공 OpenAPI가 30일치 데이터를 제공하지 않아 `availablePeriod`가 약 20일로 단축됨(예: 2026-07-26 조회 시 `endDate: 2026-08-14`). 백엔드 로직 자체 문제가 아닌 원천 데이터 문제로 확인 — 담당자에게 문의 완료, 응답 대기 중.
  - 프론트 현황: `DetailPage.tsx`의 캘린더 `maxDate`는 `오늘+29일` 하드코딩 유지. 데이터 없는 날짜는 "—"로 폴백되므로 크래시 없음. OpenAPI 정상화 시 자동 해결; 만약 30일 미만으로 확정된다면 `maxDate`를 `forecast.availablePeriod.endDate` 기준 동적 처리로 수정 필요
- [x] **대체 스팟 추천 / 함께 가기 좋아요 엔드포인트** — 백엔드에 `/suggestions`·`/companions` 엔드포인트가 추가됨으로써 해결. 프론트 연동 완료 (§4.3, §5)

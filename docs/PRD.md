# PRD — 부산 눈치게임 (Visit Busan)

작성 기준일: 2026-09-20 · 근거: 현재 코드베이스(`frontend/`), 원 제안서(`『2026 관광데이터 활용 공모전』 제안서_숨은길(옥진경).pdf`)

> 이 문서는 공모전 제안 당시 작성했던 기획안이 아니라, **실제로 완성된 서비스**를 기준으로 다시 작성한 PRD다. 제안서 대비 달라진 점은 각 절에 명시한다.

## 1. 한 줄 요약
부산 주요 관광지의 오늘/향후 30일 혼잡도를 예보하고, 한가한 대체지와 부산의 숨은 명소를 추천해 "사람 없을 때 갈걸"이라는 후회를 없애는 여행 타이밍 서비스입니다.

## 2. 현재 상태
메인·목록·상세 3개 화면이 실 백엔드(`https://busan-timing-backend.onrender.com`, Spring Boot, `/v3/api-docs`)와 완전히 연동되어 있고, 이 저장소(`frontend/`)에는 목업 데이터가 전혀 남아있지 않다. 제안서에 명시한 핵심 기능(혼잡도 지도, 검색·필터, 혼잡도 예보 캘린더, 대체지 추천, 연관 관광지, 축제 연동, 주차장 안내)이 모두 구현·배포됐고, `main` 브랜치 푸시 시 GitHub Actions로 Vercel에 자동 배포된다. 남은 것은 기능 구현이 아니라 운영 단계 과제(애널리틱스, 장애 대응, 백엔드 인프라 안정화)다. 자세한 기능별 현황은 §4, 남은 과제는 §8 참고.

## 3. 배경 및 문제 정의

### 3.1 문제의식
- 모처럼의 여행에서 유명 관광지의 끝없는 줄, 사진 한 장 찍기 힘든 인파를 마주하면 여행이 휴식이 아닌 "노동"이 된다 — 누구나 겪어본 "사람 없을 때 올걸"이라는 후회, 즉 "실패한 눈치게임"이 문제의 출발점
- 인기 관광지는 시간대·요일에 따라 혼잡도 편차가 커서, 사전 정보 없이 방문하면 대기·인파에 시간을 낭비한다
- 기존 여행 서비스(야놀자, 마이리얼트립 등)는 "어디가 맛있는지·예쁜지"에만 집중돼 있고, "언제 가야 쾌적한가"라는, 여행의 질을 실제로 좌우하는 요소는 다루지 않는다. 네이버·구글맵의 혼잡 시간대 기능도 과거 데이터 기반 요일·시간대 패턴만 줄 뿐, 특정 날짜를 앞서 예보하지는 않는다
- 특정 관광지에 관광객이 쏠리면 시설 훼손·지역 주민 불편·관광 품질 저하로 이어져, 부산 관광 경쟁력 자체가 장기적으로 약화된다 — 이는 여행자 개인의 문제가 아니라 부산 관광 생태계 전체의 과제

### 3.2 해결 방안 및 필요성
- **해결 방안**: 부산 주요 관광지의 향후 30일 혼잡도를 예보하고, 혼잡할 땐 같은 테마의 대체 관광지를, 한산할 땐 숨은명소를 그 자리에서 자동으로 연결한다. 사용자가 직접 비교·검색하지 않아도 "혼잡 정보 확인 → 대안 발견"이 한 화면에서 끝나는 흐름은 기존 여행 플랫폼이 제공하지 못한 방식이다
- **필요성**: 여행 전부터 목적지의 혼잡도를 미리 확인하고 일정을 조정할 수 있다면, 현장에서 맞닥뜨리는 실망과 시간 낭비를 줄일 수 있다. "언제 가야 쾌적한가"를 여행 계획 단계에서 최대 30일 앞서 예보 형태로 제공하는 전문 서비스는 국내에 없었고, 부산을 거점으로 이 "타이밍 정보" 공백을 선점하는 것이 서비스의 시장 경쟁력이자 존재 이유다
- 개인의 자발적 선택(한산한 날짜·장소 고르기)이 곧 부산 전역의 관광 수요 분산 효과로 이어지는 구조라, 개인 편의 추구와 도시 단위 관광 품질 관리가 같은 행동 하나로 동시에 해결된다

### 3.3 기대효과
- **사용자**: 인파에 치여 "다시는 안 온다"는 부정적 인상 대신, 여유로운 부산을 만끽하는 경험으로 여행 만족도가 높아지고 "다시 찾고 싶은 도시"라는 인식으로 이어진다
- **부산 관광 생태계**: 인기 관광지 쏠림 완화로 시설·환경 부담이 줄고, 숨은명소가 자연스럽게 노출되면서 관광 자원이 특정 스팟에 편중되지 않고 다양화된다 — 시설 훼손·주민 불편으로 이어지는 악순환을 데이터 기반으로 끊는 구조
- **서비스/사업 관점**: "특정 날짜의 혼잡 예보"라는, 국내 여행 플랫폼이 채우지 못한 카테고리를 부산에서 먼저 선점 — §9의 지역 확장·B2B 연계 등 후속 로드맵의 근거가 되는 차별점

## 4. 타깃
부산 방문/거주자 중 혼잡을 피해 여행 동선을 짜려는 10~30대. 서비스명 "부산 눈치게임 - 여행 가기 좋은 날"에서 드러나듯, 밈성 있는 게임화 프레이밍으로 SNS 공유·바이럴을 노린다.

## 5. 목표 (Goals) / Non-goals
1. 부산 구별 혼잡도를 지도 위에서 즉시 파악
2. 혼잡도 낮은 "숨은명소"와 인기 "핫플레이스"를 구분해 추천
3. 스팟 상세에서 요일·기간별 혼잡도 예보로 방문 시점 계획 지원
4. 혼잡할 땐 대체지를, 관심 있을 땐 연관 관광지를 그 자리에서 바로 제시
5. 검색·구 필터로 원하는 스팟을 빠르게 탐색

### Non-goals (현재 스코프 아님)
- 실시간 인파 데이터(현재는 예측치 기반 30일 예보이며, T맵 등 유료 실시간 API 연동은 수익화 이후 과제)
- 예약, 티켓팅, 길찾기 등 트랜잭션 기능
- 회원가입/로그인, 개인화 추천, 관심 스팟 저장
- 다국어 지원, 부산 외 지역 확장 (§9 로드맵 참고)

## 6. 핵심 기능 — 완성본 기준

### 6.1 메인 (`/`)
- `GET /api/main`으로 구별 혼잡도, 주간/월간 "눈치게임 접전지"(방문 많은 순 랭킹), "이달의 히든 플레이스"(향후 30일 예측 혼잡도 평균 최저 스팟) 조회
- 카카오맵에 부산 구별 폴리곤을 혼잡도 레벨(0~5) 색상으로 표시, 구 hover 시 혼잡도 게이지 + 오늘의 추천 관광지 팝업
- 구 클릭 시 `/list?district={code}`로 이동
- 눈치게임 접전지 카드(`HotPlaceCard`, 순위 배지), 숨은명소 카드(`HiddenPlaceCard`) — 목록 페이지 `SpotCard`와 시각 언어(호버 accent, CTA 화살표) 통일

### 6.2 목록 (`/list`)
- `GET /api/places`로 검색·구 필터·정렬·페이지네이션 조회
- 스팟 검색(`?q=`), 구 필터(`?district=`)
- 혼잡한 구 선택 시 여유 구 TOP3 배너(`CongestionBanner`) — PC는 스트립+팝업, 모바일은 칩 배너
- 스팟 카드(`SpotCard`) — 오늘 기준 혼잡도(`todayCongestion`) 표시, 이미지 없는 스팟은 기본 이미지(`default_card.png`)로 폴백, 혼잡도 미집계(레벨 0)는 "집계중" 스탬프로 구분해 숫자 노출 없이 처리
- 페이지네이션 — 5페이지 고정 그룹 창, 그룹 단위 이전/다음 이동

### 6.3 상세 (`/detail/:spotId`)
- 스팟 기본정보(`GET /api/places/{id}`): 이름·주소·설명·이미지·오늘 혼잡도·주차장 검색 링크(`parkingSearchUrl`, 백엔드가 주소 포함 URL로 제공해 동명 관광지 오검색 문제 해결됨)
- 기간별 혼잡도 예보 캘린더(`GET /api/places/{id}/forecast`): 최대 7일 구간 선택 + 다음 7일 비교, 날짜 hover/탭 시 레벨별 코멘트·축제 정보 팝업, 가장 한가한 날 "★ 추천" 배지
- 요일별 혼잡 패턴(`GET /api/places/{id}/congestion-pattern`): 요일 평균 혼잡도, 혼잡/여유 요일 강조
- 축제(`GET /api/places/{id}/festivals`): 향후 30일 겹치는 축제 목록 + 캘린더 날짜에 깃발 배지, 캘린더·리스트·팝업 3곳 상호 하이라이트
- 대체 스팟 추천(`GET /api/places/{id}/suggestions`): 오늘 혼잡도 레벨 4 이상일 때만 노출, "내 주변"(거리순)·"취향저격"(카테고리 유사) 탭
- 함께 가기 좋아요(연관 관광지, `GET /api/places/{id}/companions`): 결과 있을 때만 섹션 노출, 새로고침으로 재조회
- 조회수 카운트(`POST /api/places/{id}/views`): 마운트 시 1회 호출, 실패해도 화면 영향 없음

### 6.4 혼잡도 시스템 (`src/utils/congestion.ts`)
- 백엔드가 내려주는 `score`(0~100, 미집계 시 `null`)를 프론트에서 레벨(0~5)로 재매핑 — 20%p 균등 구간(0~20/21~40/41~60/61~80/81~100), `null`은 레벨 0("집계중")
- 레벨 → 색상/이미지/라벨 변환이 이 파일 한 곳에 집중돼 있고, 지도·카드·차트 등 모든 컴포넌트가 재사용(임계값 재구현 금지)
- "혼잡도"는 항상 **오늘 기준**(`todayCongestion`)으로 통일 — 제안서 초기 구현에서 화면마다 "지난 7일 평균"/"당일" 기준이 섞여 있던 문제를 해소함

## 7. 제안서 대비 구현 현황

### 7.1 데이터 활용 방안 (원 제안서 §3)
프론트는 원천 공공 OpenAPI를 직접 호출하지 않고, 커스텀 백엔드(Spring)를 통해서만 데이터를 받는다. 백엔드가 내부적으로 아래 API를 그대로 쓰는지는 프론트 저장소 범위 밖이라 미확인이며, "상태"는 해당 데이터를 쓰는 **프론트 기능**의 완료 여부다.

| # | 원 계획 API | 적용 기능 | 상태 |
|---|---|---|---|
| 1 | 한국관광공사_관광지 집중률 방문자 추이 예측 정보 API | 메인 지도, 상세 혼잡도 예보 캘린더·요일별 패턴·대체지 추천 | ✅ 완성 |
| 2 | 한국관광공사_관광지별 연관 관광지 정보 API | 함께 가기 좋아요 | ✅ 완성 (백엔드 `/companions`) |
| 3 | 한국관광공사_국문_관광정보 서비스 API | 목록 카드, 상세 기본정보/이미지 | ✅ 완성 |
| 4 | 부산광역시_축제정보서비스 API | 상세 축제 배너·캘린더 도트 | ✅ 완성 |
| 5 | 카카오맵 API | 메인 지도 렌더링, 상세 주차장 링크 | ✅ 완성 (주차장은 백엔드가 내려주는 URL을 그대로 사용, 프론트에서 카카오 Local API 직접 호출 없음) |
| 6 | 브이월드(국토교통부) 연속지적도형정보(읍면동경계), 2026-09-15(202609판) 갱신 | 메인 지도 구·동 경계 폴리곤 렌더링 (`public/busan_districts.geojson`) | ✅ 완성 |

### 7.2 제안서 화면 설계 대비 변경 사항
- "구별·키워드별 검색 + 저혼잡도순 정렬"은 그대로 구현. 단 "구 선택 시 필터 자동 적용된 상태로 진입"은 목록 페이지 쿼리 파라미터(`?district=`)로 동일하게 동작
- "혼잡 구 선택 시 여유 구 TOP3 배너"는 `CongestionBanner`로 구현, `districtSuggestion.visible` 값으로 노출 여부를 백엔드가 제어
- "앞으로 7일 혼잡도 아이콘 + 이후 7일 비교"는 제안서 와이어프레임 그대로 유지, 캘린더 UI는 이후 자체 리디자인(스탬프 확대, 상호 하이라이트, 추천 배지 추가)으로 고도화됨
- 요일별 혼잡 패턴 차트는 제안서에 없던 기능이나, 백엔드가 제공해 함께 구현

## 8. 남은 과제 / 리스크

### 완료되지 않은 항목
- **애널리틱스 미연동**: GA4/Amplitude 등 도구 선정부터 미착수 — §9 KPI는 정의만 돼 있고 실측 불가
- **API 장애 폴백 UI 최소 수준**: react-query 기본 캐싱은 있으나, 재시도·백오프·정교한 폴백은 없음(현재는 `isError` 시 에러 메시지 + 상세 페이지 예보 영역만 재시도 버튼 제공)
- **예측 정확도 미검증**: 혼잡도 예보의 근거가 실제 방문 패턴과 얼마나 맞는지 검증 안 됨 — 서비스 신뢰의 근간과 직결
- **데이터 커버리지 공백**: 백엔드 미등록 스팟은 요일별 패턴이 빈 배열로 오는 등 스팟별 편차 존재

### 외부 의존 리스크
- **백엔드 인프라**: Render 무료 티어 배포로 콜드스타트·트래픽 급증 시 응답 지연 가능. 상용화 가능한 구성인지 미확인 — 백엔드 저장소 소관
- **카카오 플랫폼 의존**: 지도 렌더링이 카카오맵 SDK에 결속, 정책/과금 변경 시 핵심 기능 직접 영향
- **공공데이터 원천 불안정성**: 예보 가용 기간이 원천 API 사정으로 30일에서 축소된 전례 있음 — 프론트가 통제 불가

## 9. 향후 발전 방향 (제안서 §4, 현재 스코프 아님)
아래는 제안서에 명시된 로드맵이며, 착수 여부는 M1(애널리틱스) 실측 이후 재검토한다. 실시간 혼잡
데이터 고도화(T맵 등 유료 실시간 API 연동)는 로드맵에서 제외 — 네이버 지도 등 경쟁 서비스가 이미
제공 중인 영역이라, 이 서비스가 차별화 축으로 내세운 "예측 중심" 포지셔닝과 상충된다고 판단.

### 단기 — 현재 구조 확장

| 항목 | 내용 | 현재 상태 |
|---|---|---|
| 지역 확장 | 제주·서울·경주 등으로 도시 선택 통합 구조 확장 | 미착수 (구조상 5자리 행정코드 기반이라 확장 자체는 어렵지 않음) |
| 글로벌 서비스 | 영어·일본어·중국어 다국어 지원 | 미착수 |
| B2B·B2G 연계 | 혼잡 시간대 인근 상권 쿠폰 노출, 지자체 대상 혼잡 데이터 제공 | 미착수 |

### 중장기 — 로그인 기반 구축 이후

| 항목 | 내용 | 현재 상태 |
|---|---|---|
| AI 여행 로드맵 추천 | 이동 패턴·관심사 데이터 기반 맞춤 코스 추천 | 미착수 — 로그인/개인화 부재로 전제 조건 자체가 없음, 로그인 도입이 선행되어야 함 |

## 10. 성공 지표 (KPI) — 정의만 완료, 실측은 애널리틱스 연동 이후

| 지표 | 정의 | 목표 |
|---|---|---|
| 지도→목록 전환율 | 메인 구 클릭 후 `/list` 진입 세션 비율 | ≥ 40% |
| 검색→상세 전환율 | `/list`에서 검색/필터 사용 후 `/detail` 이동 비율 | ≥ 30% |
| 숨은명소 클릭 점유율 | 숨은명소 클릭 / (숨은명소+핫플레이스 클릭) | ≥ 25% |
| 예보 캘린더 상호작용률 | 상세 방문 중 날짜 재선택 1회 이상 비율 | ≥ 20% |
| 재방문율 | 7일 내 재방문 세션 비율 | ≥ 15% |

숫자는 확정치가 아니라 초기 기준선이며, 로그인/개인화가 없는 현재 구조상 재방문율 목표는 구조적 한계가 있을 수 있음 — 실측 후 재조정.

## 11. 기술 스택
- React 18 + Vite, TypeScript, `@tanstack/react-query`(데이터 페칭), React Router
- CSS Modules + `src/styles/variables.css` 공유 토큰 (Primary `#088bff`, Secondary `#f55220`)
- 카카오맵 SDK(전역 스크립트 로드), `public/busan_districts.geojson`
- 배포: GitHub Actions → Vercel 자동 배포(`main` 푸시 시)
- 미사용 설치 패키지: `zustand`, `recharts`, `dayjs` — 지금까지 없어도 구현에 문제 없었음, 필요 시점 전까지 추가 검토 보류
- 백엔드: Spring Boot, `busan-timing-backend.onrender.com`, 스펙은 `/v3/api-docs` (이 저장소 범위 밖)
